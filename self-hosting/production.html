Production checklist

Before production:

  • Terminate TLS, use secure cookies, set exact public/trusted origins, and keep API/web headers behind a reviewed reverse proxy.
  • Generate unique high-entropy auth, encryption, database, S3, and SeaweedFS secrets; use a secret manager and rehearse rotation.
  • Keep PostgreSQL, Valkey, SeaweedFS administration, and Mailpit off public networks. Replace Mailpit with an authenticated production SMTP service.
  • Preserve separate migrator, API, and worker roles. Audit BYPASSRLS access, test RLS policies, and alert on privileged direct connections. Keep the expected role identity variables aligned with PostgreSQL; API and worker startup require session_user = current_user = expected role and verify NOSUPERUSER, NOBYPASSRLS, NOCREATEDB, NOCREATEROLE, NOREPLICATION, and NOINHERIT. Runtime roles must have no direct or recursively reachable memberships, including PostgreSQL capability roles such as pg_execute_server_program, server-file access, signal/checkpoint, subscription, maintenance, monitoring, and pg_read_all_* roles. Treat any justified exception as an explicit, reviewed allowlist entry. Keep worker access to authentication data limited to the non-secret user identity columns. Production configuration requires the literal roles fiscal_fox_app, fiscal_fox_worker, and fiscal_fox_migrator; custom runtime role names fail before SQL startup.
  • Configure rate limits, request/body limits, centralized redacted logs, monitoring, job/dead-letter alerts, database/storage capacity alerts, and clock synchronization.
  • Deploy only a release whose checks passed. Build images without cache and keep the exact build you tested.
  • Scan/sign images, pin deployment artifacts, publish release notes, and keep a rollback image and compatible database plan.
  • Schedule encrypted off-site PostgreSQL plus SeaweedFS backups and perform documented restore drills with record counts and artifact SHA verification. Require an external mode-600 HMAC key for backup authenticity, rehearse key rotation, and retain old keys for the lifetime of their backups. Restore only data into a schema created by the matching release; never execute archive-provided functions, triggers, ACL helpers, or migration journals. Put the shared backup/restore operation lock on operator-owned storage and alert on stale locks. Keep retained rollback databases until post-restore validation, then remove them deliberately. A post-swap failure must keep services stopped until an operator selects and activates either the restored or rollback database.
  • Keep the external session-generation volume writable only by its initializer and read-only to API. Verify fresh deployments create a mode-600 random value; never include it in PostgreSQL backups or images.

Provider-specific readiness includes Stripe webhook replay/signature tests, DocuSign callback and legal review, Google OAuth redirect review, SMTP deliverability, and Nominatim/OSRM terms/capacity. Testing without live credentials does not prove readiness. Enabling DocuSign requires the worker integration key, user, account, private key, and valid HTTP(S) base path while API receives only the enabled flag.

Remote AI is opt-in and may disclose financial data. Complete privacy, processor, residency, retention, and incident-response review first.

Fiscal Fox has no bank connection, hosted business email, native apps, Peppol transport, or direct filing. Built-in signatures are not qualified signatures. Force overrides and privileged SQL can defeat normal accounting safeguards and must be tightly controlled.
