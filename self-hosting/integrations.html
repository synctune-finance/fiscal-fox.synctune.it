Integrations

SMTP and storage

SMTP delivery uses the configured server; local Compose points to Mailpit. SeaweedFS exposes an S3-compatible endpoint for receipts and immutable artifacts. Neither Mailpit nor development S3 credentials are production-safe.

Stripe and DocuSign

Stripe Connect supports onboarding, checkout links, webhooks, reconciliation, fees, refunds, and disputes when credentials are configured. Webhook signature verification requires STRIPE_WEBHOOK_SECRET. Checkout and refunds use direct charges in the organization's connected account, so the connected account owns the charge, Stripe fees, balance transactions, and refunds. Fiscal Fox does not create a platform application fee.

DocuSign is optional; built-in signatures remain available. Set the API's non-secret DOCUSIGN_ENABLED=true indicator only when the worker has the integration key, user/account IDs, private key, and base path. Those provider credentials belong exclusively to the worker and must never be injected into the API or web containers. Built-in evidence records consent and audit data but is not a qualified electronic signature and may not satisfy every legal use case.

Calendar and maps

Google Calendar requires OAuth credentials and the callback /api/v1/calendar-connections/google/callback. Read-only iCalendar URLs are an alternative. Nominatim and OSRM are optional conveniences; manual trip entry works without them. Respect provider usage policies and avoid sending confidential address data to public services without approval.

Document intelligence and AI

Local extraction is the default. OpenAI-compatible and Copilot SDK providers are optional. Enabling a remote provider may send receipt text or structured financial fields outside the deployment. Review retention, training, residency, and access terms, disclose the processing, minimize content, and obtain the required privacy approval. API keys are encrypted at rest, but encryption does not replace provider governance.

Provider integrations have not been verified against live Stripe, DocuSign, Google, maps, SMTP, or AI accounts. Test each provider in a staging installation before relying on it.

Peppol UBL validation

Invoice and credit-note exports implement the Peppol BIS Billing 3.0 semantic profile on UBL 2.1, including tax-category subtotals, discounts, payment data, party identifiers, invoice references, and monetary totals. Scheme codes follow OpenPeppol EAS v9.7 (released 2026-07-02). Fiscal Fox accepts only the schemes it can validate:

  • 0088 GLN
  • 0106 Dutch KVK
  • 0190 Dutch OIN
  • 0246 German GEBA

Each supported identifier has format or check-digit validation. The removed 0193 scheme and other schemes without identifier validation are rejected rather than falsely accepted. Dutch eight-digit KVK identifiers can be derived as 0106; other endpoints must be present on the finalized document. Email addresses are never endpoint identifiers.

Before a document is rendered, Fiscal Fox checks mandatory structure, supported category identity rules, Dutch NL-R-001 through NL-R-005 and NL-R-007, BR-CO-25, BR-E-02, supported EAS schemes, currency precision, line allowances, VAT breakdowns, and document arithmetic. R003 uses only an explicit buyer reference or purchase-order reference; the seller's general reference is never substituted. Intra-EU category K requires a supply date or invoice period and an explicit delivery country from the document's delivery address (BR-IC-11/12). Credit notes do not emit the seller's collection account as a refund instruction. VAT subtotals sum the line tax amounts and validate rate arithmetic with the BR-S-09/BR-CO-17 rounding tolerance.

These checks do not run the official UBL XSD or the full Peppol Schematron distribution. Fiscal Fox does not provide Peppol network transport; validate the XML with your access point's current official ruleset before sending it.
